# このプロジェクトについて
* IVRC 2026「Meal Be Back」のためのプロジェクト
* 体験者は、モータ制御の流体デバイスを通して、食べる感覚が巻き戻っていく体験をする
* 魚肉ソーセージを題材に、食べ物の大切さと、それがどこから来たのかを体験者に気づかせることが(まぁ)目的
* 新規性（仮）：流体（水）を使って食感の変化を表現している点だと考えられている。

* 魚肉ソーセージは口腔内呈示部によって仮想化する。構成は以下の通り。
  * 外装カバー：生体適合性のある医療用・食品グレードのシリコン／ゴム素材。口内に直接触れ、膨張・収縮によって食べ物の体積変化と噛み応えを再現する。交換可能な構造。
  * 流体制御部：ステッピングモータ駆動のシリンジポンプ。カバーの膨張・収縮を行う。
    * ~~サーボモータ（SG90）によるチューブ挟み込み機構~~ → IVRC 2026 版では**落とす可能性が高い**。予算と時間の制約による。8月最終週のMTGで結論を共有する。
  * ~~咀嚼検知部（咬筋への表面筋電センサ）~~ → 制約により**実装できない可能性が高い**。今回の展示に向けては開発しない。

> **未解決（ブロッカー）**：sEMGを落としたことで、「いま噛んでいる」ことをシステムに伝える入力が無くなった。視覚・聴覚・流体のすべてがこの信号で駆動される前提で設計されていたため、代替のトリガが決まらないと視覚呈示と流体の挙動を仕様として書けない。「このプロジェクトが扱う範囲」と「ゴール」も参照すること。

# このプロジェクトが扱う範囲
* この Unity プロジェクトが扱うのは視覚呈示。
* まず体験者を初期化シーン（`SetupScene_SteamRuntime`）に移す。ここでチームメンバが机の高さをキャリブレーションし、本番の準備を行う。
* 次に `WaterScene_SteamRuntime` に移る。ここからクイズ体験が始まる。体験者の目の前には机があり、シーン全体は海中のような見た目で、海岸線・ゴッドレイ・水面が見えている。このシーンは見た目においては実装が行われている（はず）。今後、リファクタリング等が必要かもしれない

* `[未定 — チームで決める必要がある：クイズのインタラクションの流れ、sEMGを落とした今、食べ物の状態変化を何がトリガするのか、体験中にデバイスの充填率をどう駆動するのか]`

# なぜ重要なのか
* 日本では、食への感謝が食育基本法に明記されており、「いただきます」も食材の命を受け取る行為として解釈されてきた。ただ、制度や言葉として命への態度が支えられていても、皿の上の料理から、その手前にあった生き物の姿を思い浮かべる部分は個人の想像力に委ねられたままになっている。
* このプロジェクトはそこを埋めることを狙う。咀嚼の過程を逆再生し、口の中で食べ物が元の生き物へと巻き戻っていく感覚を、映像と逆再生の咀嚼音と合わせて提示することで、命を食べているという事実に自分の身体を通して直接触れさせる。

# ゴール
* クイズ形式の食育体験として成立させる。体験者は「原材料が海産物だと思うもの」を選び、それを咀嚼することで、元の生き物が自分の口から出てくるのを確認する。
* 3つのチャネル、すなわち視覚的な食べ物の状態変化、逆再生の咀嚼音、口腔内の膨張・収縮を1つのシステムに統合し、体験者の動作と提示内容が結びついた状態を保つ。
    * 予稿ではこの結びつきを「咀嚼動作をリアルタイムに入力として使う」ことで実現するとしていた。sEMGを落とした現在、その仕組みは未定義である。代替の入力を決めるか、IVRC 2026 版で実際に達成できる水準にゴールを書き直すか、どちらかが必要。

# いつまでに完成させるか
* IVRC 2026 の展示（2026年9月6〜9日、富山）まで。

# 制約（内部向け／AIエージェント向け）
* **予算**：ハードウェアとシステム開発に使えるのは概ね5,000円以内。すべてゼロから作るか、安いものを組み合わせるしかない。したがって、AIエージェントにあたっては、実現不可な雑なアイデアを出すな。

* **スキル**：メンバ間で開発スキルにかなり差がある可能性がある。タスクを割り振るときはこれを前提にすること。

## 1. 咀嚼タイミング：Wizard of Oz

### 1.1 なぜこれにするか `[確定]`
IVRC 2026 では sEMG を落とす。完全にシステム主導（オープンループ）にすると、デバイスの体積と体験者の実際の顎の動きが必ずズレていき、しかもそのズレは体験者に直接知覚される。一方、机の高さのキャリブレーションのために運営が1人張り付く前提になっているので、その人間がループを閉じればよい。ハードウェアのコストはゼロ、実装コストも小さい。

### 1.2 オペレータ用コンソール `[提案]`
HMD の描画をしている PC 上で動かす。デスクトップ側のモニタに、体験者のミラー映像と現在の状態を出す Unity の Canvas をもう1枚用意する。

キー割り当て（キーボードのみ、片手で足りる、マウス不要）：

| キー | 動作 |
| --- | --- |
| `Space` | 咀嚼ビート。顎が閉じるたびにオペレータが押す |
| `R` | 再同期。デバイスの充填率と視覚の段階を、本来あるべき状態に強制的に合わせる |
| `N` | 次の巻き戻し段階へ手動で進める |
| `B` | 1段階戻す（押し間違いからの復帰用） |
| `E` | 緊急停止。流体を抜き、映像を止める |

設計上のルール：
* すべてのキーは、冪等であるか、簡単に取り消せること。オペレータは必ず押し間違える。
* どのキーも、口の中で急激な圧力変化を起こしてはならない。`E` は必ず抜く方向であり、入れる方向には動かさない。
* コンソールには現在の段階、現在の充填率、最後のビートからの経過時間を表示する。交代した人がすぐ引き継げるようにするため。

### 1.3 ハイブリッド方式 `[有力]`
純粋な WoZ は、オペレータが全セッションを通して見続けることを要求する。現実的な折衷案は以下。
* システム側は**デフォルトのリズム**（§2参照）を回し続ける。オペレータの注意が切れても体験は止まらない。
* オペレータの `Space` は、毎回のビートを一から発火させるのではなく、回っているリズムの**位相を補正する**ものとして扱う。つまり観測された押下のほうへ位相をずらす。ただし1ビートあたりのずらし幅に上限（例えば150ms）を設け、1回の押し間違いでデバイスが跳ねないようにする。
* この方式は degradation が緩やか。オペレータが完璧ならクローズドループとして振る舞い、誰も操作しなければオープンループのペーサーとして振る舞う。

### 1.4 オペレータ用の手順書 `[提案]`
ブース用にA4 1枚のカードを作る。オペレータは、その体験を一度も回したことがないメンバである可能性がある。
* どこを見るか（HMD ではなく顎のライン）。
* 何をいつ言うか。基本は最小限で、体験中は理想的には何も言わない。
* 復帰手順：体験者が明らかにズレたら `R` を押す。`Space` で追いかけようとしないこと。

## 2. 「こうしてください」と言わずにテンポを作る

基本方針：体験者は指示されるのではなく、テンポに**引き込まれる**べきである。画面に「噛んでください」と出した時点で体験は壊れる。

### 2.1 どのチャネルでテンポを作るか `[提案]`
このセクションはあとでちゃんと検討すること。
~~1. **デバイス自身をメトロノームにする。** カバーが膨らむと歯に物理的に押し当たる。この押し返しは「いま噛め」の合図として最も強く、追加のハードは要らない。収縮すれば「口を開けろ」になる。~~
~~2. **次に音。** 人間のリズム同期は視覚より聴覚のほうが圧倒的に強い。逆再生の咀嚼音を先に鳴らし、デバイスがそれに追従する。~~
~~3. **視覚は進捗であって合図ではない。** 視覚は「巻き戻りがどこまで進んだか」を伝える役に徹し、「いつ動くか」は伝えない。~~

~~オフセットの目安（実際は感覚で詰める）：音を t=0、流体を t≈+80〜120ms、視覚の段階変化を t≈+150ms。わずかな遅れは因果として読まれる。~~

### 2.2 「ゆっくり噛んで」を言わずに伝える `[提案]`
UX の観点では言わないほうがよい。生成AIから出てきた案は以下の3つ。
* **最初から遅く始め、速いテンポを一度も見せない。** 最初のビートから1噛み1.5〜2.0秒程度にする。速いテンポを提示しなければ、遅さは制約ではなく基準になる。
* **カバーを物理的に噛み切りにくくする。** 肉厚を増やす、硬度を上げる。これは予稿自身の設計意図（3.2節：肉厚と硬度特性で初期抵抗や咬合感を表現する）とそのまま一致するし、機構としてゆっくり噛むことを強制できる。
* **1個目をチュートリアルとして使う。** 1個目だけ極端に遅くする。2個目以降はテンポが身体に入っている。

## 3. オープンループのズレを見えなくする

### 3.1 連続対応ではなく離散イベントにする `[提案]`
顎の角度とカバーの体積を連続的に対応させては**いけない**。連続対応はズレた瞬間に嘘だとバレる。代わりに、

> 1噛み ＝ 巻き戻り1段階

とする。離散イベントにしておけば、±200ms 程度のズレがあっても因果関係として読まれる。WoZ／オープンループのシステムを「反応している」と感じさせるうえで、これが一番効く判断だと思う。

### 3.2 段階は少なく、大きく `[提案]`
4〜6段階。各段階の見た目の差をはっきりさせる。魚肉ソーセージなら例えば以下。

`ソーセージ → すり身 → 身のかたまり → 切り身 → 魚まるごと → 生きている魚`

1段階あたりの変化が大きいほど、タイミング精度への要求は下がる。

### 3.3 ズレは演出のせいにする `[提案]`
そもそも食べ物が巻き戻っている時点で物理法則の外にある。多少の不一致は、システムのエラーではなく逆再生という現象の一部として吸収できる。むしろこれを利用して、機械的に正確というより少し不気味な巻き戻り方にしたほうがよい。

## 4.「口の中で魚が生きている」`[要検証]` — 一番価値が高く、一番早く検証すべきアイデア

巻き戻りの最終段階が「魚」ではなく「**生きている**魚」だったら、コンセプトが映像だけでなく身体的に着地する。体験者は、解放する直前に自分の口の中で命を感じることになる。おそらくこの企画が本来狙っているものはこれ。

### 4.1 削った後に残るハードで成立しうる理由
ステッピングモータ駆動のシリンジポンプは位置制御のアクチュエータである。ゆっくりした充填・排出のランプだけでなく、小さく速い振動も出せる。「生きている」を感じさせるのに大きな動きは要らない。必要なのは**小さく、不規則で、自分から起きたように見える**動きである。

### 4.2 動きのボキャブラリ `[提案]`
名前付きの波形を定義しておき、体験側がそれを並べて使う。

| 名前 | 性質 | 目安のパラメータ |
| --- | --- | --- |
| `breathe` | 遅く、規則的、かろうじて分かる程度 | 0.4〜0.8Hz、振幅は非常に小さく |
| `twitch` | 一回きりの鋭い跳ね | 速いステップのバースト1回、100ms未満 |
| `thrash` | 暴れる | `twitch` を不規則な間隔で3〜6回、約1秒 |
| `still` | 死んでいる／動かない | 動きなし |

並べ方の案：巻き戻りの序盤は `still` → 「魚まるごと」の段階で最初の単発の `twitch`（ここで体験者が「動いた」と気づく）→ `breathe` → 解放直前に `thrash`。

### 4.3 効くのは不規則さ `[提案]`
規則的な振動はモータに感じられる。不規則な振動は生き物に感じられる。イベント間隔をランダムにする（指数分布っぽい分布から引き、下限を設ける、など）。重要なのは、この動きを咀嚼のリズムに**位相同期させないこと**。魚が自分のスケジュールで動いているからこそ、別の主体として読まれる。

### 4.4 他の感覚で補強する `[提案]`
`twitch` に合わせて、VR 内の魚が同時にビクッと跳ねる、短い水っぽい跳ねる音を鳴らす。触覚側で出せる振幅は小さいので、印象の大半は他の2チャネルが担う。クロスモーダルな増幅は定石だし、コストも安い。

### 4.5 解放の瞬間 `[提案]`
締めとして一番有力なのは、体験者が口を開けると魚が海へ泳ぎ去っていく画。一人称で、カメラのすぐ下から魚が出て、視界を横切り、群れに合流する。記憶に残るのはこの絵なので、他を削ってもここの予算は守ること。

### 4.6 手を出す前に確かめること
* チューブとカバーのコンプライアンスがある状態で、ステッパが必要な周波数の振動を実際に知覚できるレベルで出せるのか。コンプライアンスがローパスとして効いて、面白い成分が全部消える可能性がある。**設計を進める前に、まず机上で試すこと。**
* チューブは硬く、短いほうが有利。空気より水（非圧縮）のほうが有利。
* 圧力の上限を必ずハードで持つこと。「生きている」と読める振幅は、不快に感じる領域よりはるかに下でよい。ここは小さくて構わない。狙いは繊細さであって力ではない。
* 驚かせるリスク。口の中で急に何かが動くと、強く噛んでしまったり、えづいたりする。徐々に入ること。最初の `twitch` が一番小さくあるべき。

## 5. 視覚での補償

デバイスが予稿の想定より弱くなった分、視覚チャネルが体験の重みを多く背負う。作業時間あたりの効果が大きい順に、安く効くものを挙げる。

* **1噛みごとに世界が反応する `[提案]`** — 噛むたびにカメラのすぐ下から泡が湧く、光がフラッシュする、水が一瞬歪む。噛むたびに世界が応答すれば、触覚の弱さは相対的に目立たなくなる。
* **決め絵に集中投資する `[提案]`** — §4.5。よくできたカット1つは、そこそこのカット5つに勝つ。
* **URP の Volume を詰める `[提案]`** — Bloom、Color Grading、水中フォグ、コースティクス、ゴッドレイ。`WaterScene_SteamRuntime` は既にあるので、新規開発ではなくパラメータ調整で済む。
* **魚の群れ `[提案]`** — GPU インスタンシングで数十匹泳がせる。無料アセットで足りる。海の広がりが出ると、海底に机があるという不条理がより効く。

## 6. Unity とハードウェアのインタフェース `[提案]`

早めに決めておくと、ソフト側とハード側がモックを使って並行で進められる。

シリアル経由の行単位 ASCII、改行終端。Unity 側がマスタ。

```
FILL <0-100>        目標の充填率を設定する
WAVE <name>         名前付きの動きを開始する（breathe|twitch|thrash|still）
STOP                動作を止め、現在位置を保持する
VENT                安全な最小位置まで引き戻す
PING                → PONG（生存確認）
```

ASCII にする理由：シリアルモニタから手で叩いてデバッグできるから。ファームウェア側は、Unity が何を送ってきても自分で安全上限（最大充填量、最大速度、最大圧力）を守ること。ホストを信用しない。

Unity 側には**モックのシリアルデバイス**を用意し、ハードが手元に無くても視覚側の作業が止まらないようにする。
